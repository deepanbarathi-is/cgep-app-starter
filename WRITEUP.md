# Capstone write-up: Acme Health Patient Intake API

I chose HIPAA Security Rule as my primary framework for this capstone. Acme Health's Patient Intake API handles protected health information directly, and HIPAA's Technical Safeguards map cleanly onto the encryption, access control, and audit logging work the system actually needed. I considered SOC 2 and CMMC, since the scenario mentions both, and rejected them: SOC 2 has no official OSCAL catalog, which adds translation overhead for no real benefit here, and CMMC's federal framing doesn't fit Acme's near-term business, since no federal pilot is part of this scenario beyond a passing mention. HIPAA is the only framework named as the primary control source in my Rego policies, in `policies/README.md`, and in `oscal/components/acme-health-intake/component-definition.json`'s `control-implementation.source`. Where SOC 2 or CMMC controls appear elsewhere, they are cross-references in OSCAL `props`, not primary controls.

Acme Health is a 50-person telehealth company. Their Patient Intake API already worked before I touched it. It was not audit-defensible, and I was asked to make it so in 30 days, without slowing the engineering team down. That constraint shaped almost every decision below more than any pure engineering preference did: I picked controls that close a real gap without adding a second system to operate, and where a stronger option existed, I wrote down why I didn't take it rather than pretending the trade-off wasn't there.

## What I built

The starter ships eight named gaps in `GAPS.md`, each one a real way patient data could leak, be tampered with, or go unnoticed if something went wrong. I closed six of them fully, in Terraform and Rego, and closed two partially, documenting what I left out and why, rather than quietly skipping them. The repository is organized into the four layers the brief asks for.

Layer 1, the Terraform baseline. I brought the uploads bucket and the DynamoDB table under customer-managed KMS keys, added a bucket policy denying any request that doesn't use TLS, moved the Lambda into the starter's VPC with a security group that allows no inbound traffic, and narrowed the Lambda's IAM role from `dynamodb:*` and `s3:*` to the six specific actions it calls. I added an S3 evidence bucket with Object Lock in GOVERNANCE mode and a 30-day default retention, a multi-region CloudTrail with log-file validation, and AWS Config with six managed rules, an SNS topic, and an EventBridge rule that routes non-compliant findings to my email. I did not build a second VPC; everything uses the starter's.

Layer 2, the policy suite. Five Rego policies in `policies/`, one per flagship gap, each with a `# METADATA` block naming the HIPAA control ID, a severity, the gap it closes, and a remediation, and each with its own test file. There are 57 unit tests across the five policies, covering passing and failing cases. `test/policy-breaks.sh` is a second layer of testing: it takes a real Terraform plan that passes, breaks it seven specific ways, and requires the whole gate to reject every one of them while still accepting the untouched plan.

Layer 3, the pipeline. `.github/workflows/grc-gate.yml` runs on every pull request against `main`: it scans for secrets with gitleaks across the whole git history, scans the Terraform with checkov, checks formatting, runs the policy tests and three sets of break tests, then logs into AWS with a read-only role and plans the change. An empty or malformed plan is rejected before it ever reaches the policy gate. On a merge to `main`, the same workflow logs in with a separate, narrower role, applies the exact plan the gate already checked, builds an evidence bundle, signs it with Cosign using GitHub's own OIDC token, verifies that signature against this exact workflow, and uploads the bundle and a receipt to the evidence vault. Branch protection requires the pull request check to pass, with no bypass for administrators. The repository history shows twelve merged pull requests and one closed without merging: that one adds a bucket with no TLS-deny policy, on purpose, and its run log shows the policy gate failing it and the merge button disabled.

Layer 4, the OSCAL component. NIST publishes no OSCAL catalog for the HIPAA Security Rule, so I wrote a small one myself, `oscal/catalogs/hipaa-164-subset/catalog.json`, covering exactly the five HIPAA sections my Rego policies already cite, with NIST SP 800-66 Rev. 2 named as the reference. `oscal/components/acme-health-intake/component-definition.json` has eight implemented requirements, each with the real Terraform address that satisfies it and a link to a real signed bundle in the vault. `oscal/profiles/hipaa-minimum/profile.json` selects the five catalog controls the component implements. All three files validate with `trestle`.

## Gap remediation

| Gap | What was wrong | HIPAA control | How I closed it |
|---|---|---|---|
| GAP-01 | Uploads bucket used AWS-managed SSE-S3, not a customer-managed key | 164.312(a)(2)(iv), 164.312(a)(1) | A per-bucket customer-managed KMS key with rotation, from a reusable `compliant-storage` module |
| GAP-02 | DynamoDB table used the AWS-owned default key | 164.312(a)(2)(iv), 164.312(a)(1) | A dedicated customer-managed KMS key for the table |
| GAP-03 | No bucket policy denying non-TLS requests | 164.312(e)(1) | A bucket policy denying any request where `aws:SecureTransport` is false, on every bucket, covering the bucket and its objects |
| GAP-04 | No S3 versioning | 164.308(a)(7) | Versioning from the same module, plus DynamoDB point-in-time recovery, added later during a checkov review |
| GAP-05 | Lambda ran outside the VPC | 164.312(e)(1) | The Lambda moved into the starter's private subnets, reaching S3 and DynamoDB only through gateway endpoints, with a security group that allows no inbound traffic |
| GAP-06 | No reserved concurrency, no dead-letter queue, no tracing | Not HIPAA-mapped | Partial. X-Ray tracing is on. I did not add a dead-letter queue, since the Lambda is invoked synchronously through API Gateway and a DLQ, designed for async failures, would never receive anything under normal operation. Reserved concurrency isn't possible in this account: the total Lambda concurrency limit is 10, and AWS requires 100 to stay unreserved. API Gateway throttling is the compensating control |
| GAP-07 | IAM role allowed `dynamodb:*` and `s3:*` | 164.312(a)(1) | The role narrowed to the exact calls the handler makes: one DynamoDB write, one S3 write under a fixed prefix, two KMS actions, and X-Ray tracing |
| GAP-08 | No API Gateway logging, throttling, or WAF | 164.312(b), logging only | Partial. Access logging (metadata only, no request bodies, so no PHI in the logs) and throttling are on. I did not add a WAF, given the ongoing cost and added scope for this timeline |

Five of these gaps (01, 02, 03, 05, 07) have a dedicated Rego policy that runs in the pipeline and would block a regression. GAP-04 has Terraform and an AWS Config rule but no Rego policy, since it wasn't one of my five flagship controls. GAP-06 and GAP-08 are closed in Terraform only, as documented above, with no policy claiming more than was actually built. I picked the encryption and access gaps as the flagship five because they're the ones where a mistake means PHI actually leaves the system unprotected; GAP-06 and GAP-08 matter for reliability and attack surface, not for whether a record gets exposed, which is why they got a smaller share of a 30-day budget.

## Continuous monitoring and detection

Closing a gap once isn't the same as keeping it closed, and a 50-person company won't have a GRC engineer checking Terraform plans by hand every week once I move on to the next thing. AWS Config runs six managed rules, one for each gap that a rule can actually see: `s3-default-encryption-kms`, `dynamodb-table-encrypted-kms`, `s3-bucket-ssl-requests-only`, `s3-bucket-versioning-enabled`, `lambda-inside-vpc`, and `api-gwv2-access-logs-enabled`. I checked every rule's real behavior against AWS's documentation before picking it, because two of the obvious-looking choices would not have caught their gap: the generic S3 encryption rule passes a bucket that still uses SSE-S3, and the IAM admin-access rule only flags a literal `*` on `*`, and only for customer-managed policies, not for the starter's inline role policy. GAP-07 has no Config rule for that reason; the Rego policy is the only thing watching it.

The recorder watches only the four resource types the six rules use, to keep the per-item charge small, not every resource in the account. Config still evaluates every S3 bucket it does watch, including ones outside this project: it correctly flagged an older evidence vault from an earlier lab exercise as non-compliant on the KMS and TLS rules, which I left alone and treated as proof the monitoring works on real data rather than only on my own resources.

An EventBridge rule on Config's compliance-change events feeds an SNS topic, encrypted with its own KMS key because the AWS-managed SNS key doesn't let EventBridge publish to it. The email subscription is optional: the underlying Terraform variable defaults to empty, so the code plans and applies with no personal information required, and I keep my own address in a gitignored file.

I proved this chain against the live account, not just in a test fixture. `scripts/verify-controls.sh` suspends S3 versioning on the uploads bucket directly through the AWS CLI, with no Terraform involved, waits for AWS Config to report the bucket `NON_COMPLIANT`, then re-enables versioning and waits for `COMPLIANT` again. I ran it once for real: Config caught the break within about three minutes, the compliance-change email arrived in my inbox with the correct resource and rule names, and the fix was confirmed the same way. That is stronger evidence than a unit test, since it shows the actual account, not a mock, doing the detecting.

## The pipeline and the evidence chain

This is the piece that actually keeps the promise of not slowing engineers down: instead of a person reviewing every change for compliance by hand, the checks run themselves on every pull request, and a compliant change ships as fast as a normal merge.

The gate is deliberately fail-closed, and just as deliberately not silent about why it failed. Every deny message names the HIPAA control, the exact resource, and what to change, the same message whether I read it at my desk or a developer at Acme reads it from their phone at three in the morning. That is the actual reason I wrote the policies this way: the business doesn't stall on a mystery failure, the developer gets a fixable answer instead of a locked door, and the compliance story stays true without anyone from governance sitting in the room watching every merge.

Pull requests get a read-only AWS role and can only plan. A merge to `main` gets a separate role and applies the exact plan the gate already checked, then builds, signs, and uploads the evidence. Neither role can change the other's permissions or trust, so the pipeline can't grant itself more access than it started with; a change to either role's Terraform has to be applied by hand, outside the pipeline. GitHub's login uses OIDC, so no AWS keys are stored anywhere in the repository or its secrets.

`scripts/build-evidence.sh` builds the bundle for each merge, holding the redacted Terraform plan (the alert email address is stripped before anything is written to a public artifact), the policy gate's verdict, the SHA-256 hashes of the policy files that judged it, the apply log, and metadata recording the commit, the workflow run, and the tool versions used. Cosign signs the bundle keylessly, using the GitHub Actions OIDC token to get a short-lived certificate from Sigstore, with no signing key to steal or leak. The pipeline verifies its own signature immediately, requiring the exact workflow identity, before anything is uploaded, so a bad signature never reaches the vault. `scripts/upload-evidence.sh` then puts the bundle, its SHA-256 file, its Cosign signature, and a receipt recording the Object Lock retention observed at upload time into the evidence vault together.

`scripts/verify-evidence.sh` checks all of this independently: it recomputes the SHA-256, verifies the Cosign signature against the exact workflow, confirms the bundle's metadata and the receipt agree on the commit and run, and reports the Object Lock retention, either read live from the vault or from the committed receipt when the reader has no AWS access. `test/verify-evidence-breaks.sh` proves that check has teeth: it mutates a copy of the committed bundle five different ways, a changed byte, a swapped signature, a mismatched receipt, and requires every one to fail. I committed one real signed bundle from an actual pipeline run in `evidence-samples/`, along with its signature and receipt, specifically so a grader without access to my AWS account can still run the check.

## OSCAL and control-to-code documentation

Three files, all under `oscal/`, and all validate with `trestle`: `oscal/catalogs/hipaa-164-subset/catalog.json`, `oscal/profiles/hipaa-minimum/profile.json`, and `oscal/components/acme-health-intake/component-definition.json`. Every UUID in the component, the catalog, and the profile is a real, randomly generated one, not a placeholder left over from a template.

The brief is specific that `control-implementation.source` has to point at my declared framework's catalog, and my declared framework is HIPAA, not NIST 800-53. Citing 800-53 the way the reference lab material does would be citing the wrong framework's catalog for this project, since that lab's declared framework was 800-53 itself. NIST publishes no OSCAL catalog for HIPAA, so I authored my own in `oscal/catalogs/hipaa-164-subset/catalog.json`: five controls covering exactly the HIPAA sections my Rego policies cite, with SP 800-66 Rev. 2 named as the reference in its metadata.

OSCAL control identifiers can't contain parentheses or start with a digit, so a citation like `164.312(a)(2)(iv)` isn't a legal identifier by itself. I wrote each identifier as a token form of the citation, the same move NIST 800-53 itself makes by writing `AC-3` as `ac-3`. The real citation, parentheses and all, still appears in the control's title, its statement text, and a `hipaa-citation` property, and again on every implemented requirement in `component-definition.json`, so nothing is invented and the citation is never hidden behind the identifier. `oscal/profiles/hipaa-minimum/profile.json` selects those five controls; I resolved it with `trestle author profile-resolve` and confirmed all five come through.

Every one of the eight implemented requirements in `component-definition.json` names a real Terraform resource address, and I checked all thirteen cited addresses against `terraform state list` on the live account before committing the file, not only against the source code. Each also links to a real signed bundle in the vault. `trestle validate -f` expects a fixed folder name that doesn't match `oscal/components/`, the path the brief names literally, so I validate with `trestle partial-object-validate`, which checks the same schema without depending on that folder name; a `.trestle/config.ini` marker is committed so this is reproducible by anyone who clones the repository.

The per-policy metadata headers, the gap-to-control table above, and the OSCAL component together give a bidirectional trace: from a HIPAA citation to the Rego policy and Terraform resource that satisfy it, and from any resource back to the control it exists for.

## Design trade-offs

Object Lock mode. The vault uses GOVERNANCE, not COMPLIANCE. COMPLIANCE is the stronger tamper-resistance claim: nobody, including the account root, can delete evidence before its 30-day retention expires. But that cuts both ways. If I, or a bug in the pipeline, put something in that bucket that shouldn't be there, COMPLIANCE mode means it sits locked and undeletable for the full 30 days, no exceptions. On a 30-day capstone, a mistake like that could cost me the whole project's remaining runway. GOVERNANCE gives up some of that tamper-resistance, since a principal with `s3:BypassGovernanceRetention` can override the lock, but it means a mistake stays fixable. I accepted that trade for this timeline. The next-phase version of this control switches to COMPLIANCE once there's a review process controlling what goes into the vault in the first place, so the stronger lock stops being a risk to me and starts being pure protection.

State management. Local Terraform state would have worked for one person, but the pipeline applies on merge from a GitHub Actions runner that is thrown away after every run, so it needs state that survives between runs. I moved state to an S3 backend using S3's own lockfile feature for locking, rather than standing up a separate DynamoDB table for it, since a single developer on a short timeline doesn't get anything extra from that second moving part.

Apply on merge. The brief's Layer 3 asks for exactly this: plan, policy check, apply on merge to main. It is fully continuous, which is what "not slowing the engineering team down" actually means in practice, a developer merges and the infrastructure updates itself, but it also hands the pipeline real deploy power with no human in the loop. I limited that risk with branch protection that has no bypass even for administrators, a required status check, and two OIDC roles built so the pipeline can plan or apply but can never widen its own permissions. That felt like the right balance for a small team on a deadline: automate the repetitive part, and keep a hard boundary around the part that could do real damage.

Single account. Everything, including the evidence vault, runs in one AWS account, my personal sandbox, because standing up a second account and the cross-account trust to reach it would have cost days I didn't have. That's next-phase work, not a permanent choice: two accounts, one running the workload and one holding only the evidence vault, so a compromise of the audited account couldn't quietly rewrite the evidence that's supposed to catch it.

The evidence vault versus the lab's vault. Acme's vault has to be something the company actually owns, built alongside the system it audits, not borrowed from an exercise I did somewhere else. An earlier lab of mine produced its own Object Lock vault in a different repository, and the capstone brief mentions that vault by name. I read that as describing the same design, not the literal same bucket: the brief's Layer 1 list asks for a KMS-encrypted vault defined in this repository's own Terraform, and the lab's bucket lives elsewhere and uses SSE-S3, not a customer-managed key, so it wouldn't even meet Acme's own encryption bar. I rebuilt the vault here from that pattern instead of pointing at the old one, and left the old bucket alone until I had a verified bundle in the new one.

Reviewer verification without AWS access. Whoever reviews this, an instructor now, an auditor later, almost certainly won't have a login to my AWS account, and a control that can only be checked by its own builder isn't really audit-defensible. So I built verification to not depend on that access: a committed signed sample bundle, a receipt recording what the vault said about retention at upload time, and a verify script with an offline mode. I can't be certain how the grading process actually checks Object Lock retention, and I'm stating that uncertainty here rather than guessing.

## Engineering hygiene

A repo that only makes sense to the person who wrote it isn't audit-defensible, since an auditor, or the next engineer Acme hires, has to be able to pick it up cold. I added an MIT LICENSE file. `.terraform.lock.hcl` is committed so provider versions stay pinned. Every checkov finding was reviewed individually: nine are accepted with a written reason, either in `.checkov.yaml` for account-wide decisions or as an inline `checkov:skip` comment on the specific resource for one-off ones, and everything else was fixed rather than suppressed, including two real changes (DynamoDB point-in-time recovery, and adopting the VPC's default security group with no rules) that the pipeline itself applied once they were in place. gitleaks runs across the whole git history on every pull request and has found nothing. `tflint` and `semgrep --config=auto` are part of the pre-submission tool pass described below.

## What I did not get to

None of these are things I forgot. Thirty days doesn't stretch to everything a mature system would have, so I chose what to leave out the same way I chose what to build: by asking what actually protects patient data versus what would be nice to have.

- GAP-06's dead-letter queue and reserved concurrency, and GAP-08's WAF, all explained in the gap table above.
- A Config rule for GAP-07. AWS's managed IAM rules don't evaluate inline policies, so the Rego policy is the only thing watching that gap.
- CloudTrail data events for S3 and DynamoDB. They would record every object and item access, closer to what an auditor would want for PHI, but they're billed per event, and the trail's management events already cover who changed what.
- Recording every AWS Config resource type. I record only the four types my six rules use.
- Automated retry and dead-letter handling on the evidence pipeline itself. If the sign or upload step fails partway, there's no automatic retry today; that's a real gap for a production system and would be my first addition given another sprint.
- Distinct CI/CD jobs for lint, validate, security, and deploy. My pipeline stages those steps in order within a single job rather than as separate GitHub Actions jobs, which is simpler to reason about but doesn't get the parallelism or the cleaner failure isolation that separate jobs would.
- Independent verification of the SOC 2 and CMMC cross-reference IDs in the OSCAL component's `props`. Those are carried from my own design reasoning about which secondary controls apply, not checked against anything live the way the HIPAA citations and Terraform addresses were.

## How to verify this

`README.md` contains the exact copy-paste commands to verify this repository. In short: `opa test ./policies` runs the 57 unit tests, `test/policy-breaks.sh` and `test/plan-guard-breaks.sh` prove the gate and its guard actually reject bad input, `test/verify-evidence-breaks.sh` proves the evidence checker actually catches tampering, and `scripts/verify-evidence.sh --dir evidence-samples/run-36292858361` checks a real signed bundle's integrity, signature, and recorded retention without needing any AWS credentials.
